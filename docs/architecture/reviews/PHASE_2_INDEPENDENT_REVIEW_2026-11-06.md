## 1. Verdict

**REVISE — technically credible and materially useful working investigation; not accepted as a complete Phase 2 deliverable.**

PR #179 is substantially stronger than the initial PR #180 report. Its main technical conclusions are generally supported by the pinned source and the inspected donor implementation. It correctly distinguishes current-main capability from donor-only capability, source presence from integration, test registration from test execution, and source-derived failure risks from reproduced incidents.

The report is also appropriately explicit that Phase 2 remains in progress, Gate A is not cleared, no implementation baseline is selected, and no runtime implementation is authorized.

However, this review identifies three material omissions or incomplete closures:

1. **The mainline perception pipeline is compiled and unit-tested but has no production call path into the audited main CognitiveCycle.** The report describes this as an incomplete interpretation path but does not identify the stronger, directly verifiable integration fact.
2. **The report does not preserve the separate PR #174 follow-on review obligations for contextual language/operator-intent grounding and downstream reasoning integration as distinct review findings.** It correctly separates PR #173 F-02/F-03, but the two sets of identically numbered findings must both remain traceable.
3. **The donor runtime's queue scheduling, shutdown and feedback-drain semantics are not fully mapped.** Feedback is always selected ahead of input work; shutdown can reject feedback generated by an action already being executed; and the action path discards the submission result. Existing findings cover parts of this problem, but the combined BM-11 behavior and acceptance tests are incomplete.

The report also contains a lower-priority acceptance inconsistency: its own Phase 2 exit criteria require human-cognition and MCU J.A.R.V.I.S. reference comparisons, but no corresponding comparison deliverable or explicit deferral is present in the closure plan.

These are targeted corrections. They do not invalidate the report's overall investigation, justify restarting Phase 2, or authorize donor integration.

## 3. Findings

### IR-01 — Main perception pipeline is not connected to the audited main CognitiveCycle

**Severity:** Medium  
**Confidence:** High  
**Classification:** Confirmed integration gap in the pinned main source tree

PR #179 §3, BM-02, lists `representation.cpp`, `perception_pipeline.cpp` and `cognitive_cycle.cpp` as main source evidence. It correctly says that the current cycle is not demonstrated to be a general semantic interpretation pipeline. The evidence supports a more specific conclusion.

At main SHA `1273ddbcd0087d189e01388ded2d362fb1e058d2`:

- [`cognitive_cycle.hpp`](https://github.com/methaneex-oss/MethaneX/blob/1273ddbcd0087d189e01388ded2d362fb1e058d2/core/cpp/include/jarvis/core/cognitive_cycle.hpp) does not include `perception_pipeline.hpp`, own a `PerceptionPipeline`, or expose provider registration.
- [`CognitiveCycle::run`](https://github.com/methaneex-oss/MethaneX/blob/1273ddbcd0087d189e01388ded2d362fb1e058d2/core/cpp/src/cognitive_cycle.cpp#L27-L44) passes the input event to `brain_.observe`, retrieves raw-attribute memories, reads beliefs and causal links, and constructs the reasoning problem. It does not invoke `PerceptionPipeline::process` or `RepresentationEngine::normalize`.
- [Main CMake](https://github.com/methaneex-oss/MethaneX/blob/1273ddbcd0087d189e01388ded2d362fb1e058d2/core/cpp/CMakeLists.txt#L45-L59) compiles `src/perception_pipeline.cpp`, and [test CMake](https://github.com/methaneex-oss/MethaneX/blob/1273ddbcd0087d189e01388ded2d362fb1e058d2/core/cpp/tests/CMakeLists.txt#L16-L18) registers its executable and [CTest entry](https://github.com/methaneex-oss/MethaneX/blob/1273ddbcd0087d189e01388ded2d362fb1e058d2/core/cpp/tests/CMakeLists.txt#L144).
- A bounded main-branch code search for `PerceptionPipeline` returned the header, implementation and unit test, but no production caller.

This means the main tree contains a compiled and tested perception utility, not an integrated perception path in its production CognitiveCycle. The existence of the CMake target and unit test must not be used as evidence that main observations pass through that pipeline.

The donor is materially different: at PR #97 HEAD, [`CognitiveCycle::run`](https://github.com/methaneex-oss/MethaneX/blob/c1da222e6c94aeb3f2ad000392c21fe4fc81ab25/core/cpp/src/cognitive_cycle.cpp#L236-L302) invokes the configured perception pipeline and uses its representation for subsequent memory retrieval, context formation and reasoning-adjacent processing. This is donor-only integration, not main capability.

**Required correction**

Add an explicit main/donor disposition to BM-02 and the integration findings:

- Main: perception/representation implementation exists and is compiled/tested, but no production CognitiveCycle call path was found.
- PR #97: perception is connected to the donor CognitiveCycle, subject to P2-I-037's provider-failure observability limitation.
- Do not credit main with integrated perception until a production caller and downstream dataflow are source-demonstrated.

Add this gap to the BM-01/BM-02 closure work and the interaction graph. No runtime change is authorized by this review.

### IR-03 — Donor runtime fairness and shutdown feedback semantics are not fully mapped

**Severity:** Medium  
**Confidence:** High for the control flow; operational impact is conditional on load and shutdown timing  
**Classification:** BM-11 scheduling/recovery gap; extends existing feedback findings

The report identifies queue rejection and discarded secondary feedback in P2-I-028 and P2-I-035. The donor runtime has two further boundary conditions that should be added to the BM-11 map.

1. [`CognitiveRuntime::worker_loop`](https://github.com/methaneex-oss/MethaneX/blob/c1da222e6c94aeb3f2ad000392c21fe4fc81ab25/core/cpp/src/cognitive_runtime.cpp#L223) selects a feedback item whenever `feedback_` is nonempty; it selects input work only when the feedback queue is empty. There is no visible fairness quota or aging rule in this loop. Under a sustained producer load that keeps feedback queued, input work can be delayed indefinitely.
2. [`stop()`](https://github.com/methaneex-oss/MethaneX/blob/c1da222e6c94aeb3f2ad000392c21fe4fc81ab25/core/cpp/src/cognitive_runtime.cpp#L76-L80) sets `stopping_`. [`submit_feedback`](https://github.com/methaneex-oss/MethaneX/blob/c1da222e6c94aeb3f2ad000392c21fe4fc81ab25/core/cpp/src/cognitive_runtime.cpp#L95-L123) rejects submissions while stopping. The action path submits secondary status/reason evidence from `execute_actions`, but discards the boolean return; see [the action-feedback call](https://github.com/methaneex-oss/MethaneX/blob/c1da222e6c94aeb3f2ad000392c21fe4fc81ab25/core/cpp/src/cognitive_runtime.cpp#L190-L218). If shutdown begins while a cycle is executing, that cycle can complete an external action and then have its secondary feedback rejected without the action path reporting the rejection to its caller.
3. The bounded result queue also drops its oldest result when full and increments `dropped_results`. That is an explicit loss policy, but the report does not map its effect on caller-visible completion and recovery.

These are not claims of a reproduced production outage. They are source-visible scheduling and acknowledgement semantics that matter to BM-11 and to the report's existing P2-I-028/P2-I-035 conclusions.

**Required correction**

Add the following to the BM-11 investigation and test matrix:

- Sustained feedback load while new input work is queued; prove bounded input service or document an intentional priority contract.
- Shutdown initiated during action execution; establish whether feedback is drained, persisted synchronously, rejected with a visible per-action result, or safely recoverable.
- Result-queue saturation; prove that dropped results are observable and that callers can reconcile completed work.
- Restart and retry after each shutdown/queue boundary; ensure the same external action is not blindly re-executed because its result/feedback was lost.

Do not treat `drain_on_stop` alone as proof that all feedback generated by an in-flight action is accepted: `submit_feedback` rejects while `stopping_` is true.

## 4. Findings and conclusions that are supported

The following parts of PR #179 are technically credible based on the inspected evidence:

- **Main memory/reasoning disconnect:** main `CognitiveCycle::run` retrieves memory, but its `ReasoningProblem` premises are populated from beliefs and causal links. The memory vector is not passed into that problem.
- **Main reasoning non-consumption:** the main cycle stores the reasoning result but does not use it later in the inspected function's prediction/planning/decision path.
- **Narrow reasoning implementation:** the current main reasoning engine is bounded keyed-value consistency and causal-link traversal, not evidence of the full BM-12 reasoning scope.
- **Goal formation distinction:** a supplied-goal lifecycle, progress update or intent selection is not experience-acquired candidate-goal formation.
- **Causal overclaim risk:** the main causal transition learner uses changed-state associations; its source alone does not establish intervention, confounder or counterexample control.
- **Belief/world projection distinction:** the Brain belief map and WorldModel facts/relations have different semantics; they should not be assumed to be one fully reconciled belief authority.
- **Donor/main distinction:** PR #97 has a compiled donor-side affective/developmental integration and a source-connected runtime action/consequence path. It remains a separate unmerged candidate, not current-main capability.
- **Persistence and execution findings:** P2-I-023, P2-I-029, P2-I-030, P2-I-035 and P2-I-036 identify distinct partial-commit, acknowledgement, ambiguous external-effect and recovery boundaries. They are source-derived limitations; they should not be described as reproduced incidents until failure injection is run.
- **Provider failure:** P2-I-037 correctly distinguishes a caught `perceive` exception and fallback representation from an observable provider-failure result. Its `supports noexcept` qualification is technically correct: an exception escaping a `noexcept` function terminates rather than reaching the surrounding catch. The acceptance test should validate the no-throw contract or change the interface if recoverable exceptions are required; it should not expect the current catch to recover a `noexcept` violation.
- **Authorization freshness:** P2-I-038 is properly kept as an unresolved host-boundary question, not asserted as an exploitable authorization bypass.
- **Withdrawn finding:** the report correctly withdraws P2-I-034 after discovering that Release test targets explicitly undefine `NDEBUG`. It should remain withdrawn and must not be used as a blocker.
- **Learning evidence:** exact-head PR #97 CI is meaningful test evidence. The historical DLT-002 results are useful narrow synthetic-task evidence, but the report correctly notes the old commit, single-seed/limited-context limitations and absence of a matched learning-disabled control. The runtime integration fixture is not proof of open-world learning.

The reports are not textually identical. PR #179 is materially broader: it adds the BM-01–BM-12 map, donor/runtime tracing, persistence and recovery findings, CI provenance, learning-test limitations, the later P2-I-037/P2-I-038 findings and the consolidated closure plan.

PR #180's initial report also assigns the wrong meanings to the PR #173 F-02/F-03 labels. PR #179 corrects those meanings in §14. That correction is right for the PR #173 correction record, but IR-02 above requires PR #179 to preserve the separate PR #174 follow-on review findings as well.

**Recommendation:** retain PR #179 as the canonical working Phase 2 report after targeted corrections. Do not merge PR #180 into it: both change the same path and have different bases. Preserve PR #180's branch/history until the Project Director decides whether to close it as superseded or retain it as a historical first-batch record. Do not claim that a content reconciliation is the same as Git ancestry reconciliation.
