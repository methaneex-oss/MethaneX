## 1. How to read this matrix

The matrix distinguishes four different evidence states:

- **Source present:** a candidate implementation file or type exists in the inspected source tree/build manifest.
- **Test present:** a test target or test source exists. This proves only that a test was authored and included, not that it passed in this audit or that its assertions are sufficient.
- **Integration evidence present:** a named integration suite or explicit runtime path exists. Its actual behavior still requires execution and inspection.
- **Not established:** source presence, filenames, interfaces or tests do not yet prove the intended capability, cross-layer interaction, persistence, transfer or production readiness.

No row is marked complete merely because a source file and a test with a matching name exist. A layer is accepted only when its mechanisms have demonstrated the specified behavior and all required dependencies and contracts are satisfied.

The C++ files below are **candidate implementation locations**, not declarations that every named mechanism is complete or authoritative in practice. The inspected C++ build manifest is a C++20 static library. The inspected baseline has a minimal Rust runtime and TypeScript interface files; the technology audit did not verify an integrated Python/PyTorch Brain subsystem or CUDA/Triton execution path.

## 3. Cross-layer mechanism and feedback traceability

The following paths are required by the Brain target. The arrows describe information/state influence, not a mandatory fixed execution order. Event/priority-driven cognition may skip, revisit, interrupt or parallelize stages where appropriate.

| Required feedback path | Participating layers | What must be traceable |
|---|---|---|
| Experience → representation → evidence assessment → world/knowledge update | L0 → L2 → L3/L6 | Original event, provenance, representation transformation, uncertainty and accepted/rejected update. |
| Experience → memory → retrieval → later reasoning/decision | L0/L2 → L4 → L5/L7/L10 | Which experience was retained, why it was retrieved, and how it influenced later behavior. |
| Prediction → observed outcome → prediction error → model/strategy update | L3/L7/L9 → L11/L0 → L12 → L3/L7/L9 | Prediction identity/sequence, expected outcome, actual evidence, error calculation, update attribution and later prediction change. |
| Goal → plan → decision → authorized action → verified consequence | L8 → L9 → L10 → L11/L18 → L0/L4 | Goal identity and constraints, selected plan, decision rationale, authorization, execution state, verification and outcome. |
| Contradiction → attention/reasoning → belief/memory revision → replanning | L6 → L5/L7 → L4/L3 → L9/L10 | Conflicting evidence preserved, attention allocation, reasoning path, accepted revision and downstream decision impact. |
| Self-observation → metacognitive diagnosis → candidate improvement → guarded adoption | L1/L13 → L14 → L15/L19 | Actual runtime evidence, limitation hypothesis, candidate lineage, baseline, test result, approval/adoption, monitoring and rollback. |
| Fault → isolation → recovery → reconstruction → retained failure learning | L0/L15/L16 → L4/L12 | Fault identity, preserved state, recovery authority, reconstructed-state equivalence and later behavior change. |
| Continuous event intake → priority scheduling → bounded cognitive work | L0/L5/L16/L17 | Trigger provenance, priority rationale, resource budget, interruption/resumption and starvation/backpressure metrics. |

A diagram or source-file call graph alone is insufficient. For each path, the implementation must demonstrate the actual state and information transfer, with provenance and observable consequences.

## 4. Verified C++ integration path at the inspected implementation baseline

A targeted source inspection went beyond filenames and build-manifest presence. The following path is directly visible in the inspected C++ implementation. It is evidence of meaningful existing integration, but it is not evidence that all layers or all real-world behaviors are complete.

### 4.1 Observation-to-reasoning/planning path

1. `CognitiveRuntime::submit` accepts a `CognitiveCycleInput`, optionally evaluates trigger signals, and queues work with a priority in `core/cpp/src/cognitive_runtime.cpp` (approximately lines 83–126).
2. The runtime worker consumes queued input and calls `CognitiveCycle::run`; it processes feedback work on the same worker path (`cognitive_runtime.cpp`, approximately lines 127–150 and 223).
3. `CognitiveCycle::run` retrieves prior memories before recording the current observation, including targeted action-outcome retrieval; then calls `Brain::observe` (`core/cpp/src/cognitive_cycle.cpp`, approximately lines 150–190).
4. `Brain::observe` validates the event, assigns timestamp/novelty metadata, appends it to `Memory`, assigns the durable sequence, updates Brain counters and calls `replay` and experience consolidation (`core/cpp/src/brain.cpp`, approximately lines 1124–1166).
5. The cycle sends the committed event to `PerceptionPipeline::process`, then collects beliefs, causal links, affective state, attention and disputed world facts (`cognitive_cycle.cpp`, approximately lines 238–289).
6. The cycle constructs a `ReasoningProblem`, calls `ReasoningEngine::solve`, uses supported conclusions (or observed beliefs when reasoning is invalid/empty) as simulation assumptions, and passes projections through `Brain::predict` (`cognitive_cycle.cpp`, approximately lines 290–325).
7. Reflection is computed before planning; eligible goals are selected; uncertainty combines attended evidence, disputes, reflection, predictions and perceptual confidence; candidate actions are constrained by capability availability before planning and decision (`cognitive_cycle.cpp`, approximately lines 326–410 and later decision/assessment code).
8. The selected plan's steps become decision candidates; the cycle invokes the Brain's decision engine and action model and returns assessments with the developmental context preserved (`cognitive_cycle.cpp`, approximately lines 737–767).

### 4.2 Action-to-outcome-to-learning path

1. `CognitiveRuntime::execute_actions` executes only actions present in the selected plan, not every candidate alternative. It invokes the configured adapter only for executable dispositions and records rejected, failed or verified execution status (`cognitive_runtime.cpp`, approximately lines 155–205).
2. When an action result can produce evidence, the runtime submits feedback through `CognitiveRuntime::submit_feedback`; feedback is validated before queueing (`cognitive_runtime.cpp`, approximately lines 86–125 and 200–205).
3. The worker later calls `CognitiveCycle::process_outcome`. That path resolves prediction feedback by prediction sequence/key, calls `Brain::learn` for evidence, assimilates goal progress when supplied, then refreshes affective and reflective state (`cognitive_cycle.cpp`, approximately lines 770–800).
4. `Brain::learn` appends a learning event to durable memory and calls `replay` and consolidation (`brain.cpp`, approximately lines 1168–1199).
5. In `Brain::replay`, validated prediction outcomes update prediction/attention/affective learning; validated action outcomes update capability performance and developmental strategy learning when observed consequences are available (`brain.cpp`, approximately lines 463–520 and 680–760).

This is a real code-level feedback path across runtime, cognitive cycle, memory, perception, reasoning, prediction, goals, planning, decision, execution and learning. It materially corrects any claim that the repository contains only isolated modules. It does **not** prove broad generalization, fully acquired intelligence, production action integration, complete evidence trust, or every Layer 0–19 requirement.

### 4.3 Important limits exposed by the same inspection

- The runtime uses bounded in-memory input, feedback and result queues. This establishes a local worker/queue path, not a durable distributed event scheduler or online/offline synchronization protocol.
- `Event` currently contains sequence, timestamp, source, kind and scalar attributes. It does not by itself define globally unique event identity, origin attestation, causal parent, correlation, schema version or cross-host sequence namespace.
- `Memory` journals events and stores metadata snapshots/updates, but its current `MemoryTier` enum exposes Working, Episodic, Semantic and Procedural. The full intended associative and autobiographical memory taxonomy is not represented as distinct tiers in this header.
- `KnowledgeEvidence` includes a `provenance_id`, and the knowledge model distinguishes verified from unverified origins. The general event/representation contract must still define how this identity is minted, authenticated, propagated and linked to every downstream claim.
- The inspected Rust `BrainRuntime` publicly owns its own `CognitiveState` with a beliefs map and working-memory vector. The audit confirms the duplicate state implementation exists; caller/dependency analysis is still required to determine whether it is an active competing runtime or an unused prototype.
- The inspected TypeScript `BrainTransport` exposes `observe`, `decide` and `capabilities`; the operator session uses an agent bridge transport. This is an interface contract, not proof of a complete read-only monitoring stream, lifecycle protocol, authenticated production transport or synchronized state projection.

## 5. Cross-cutting contracts required by all applicable layers

The matrix cannot be considered implementation-ready until the following contracts are specified and versioned.

1. **Canonical event contract:** event identity, source identity, provenance, sequence namespace, timestamp/clock semantics, causal/correlation links, idempotency, duplicate handling and schema version.
2. **Canonical state ownership contract:** one authoritative owner per state domain; explicit read projections; accepted mutation path; concurrency and transaction rules.
3. **Representation contract:** entity/concept/event/relation identity, attributes, temporal/spatial semantics, modality, unknown values, ambiguity and schema evolution.
4. **Evidence contract:** source provenance, independent origin, dependence, freshness, reliability, confidence semantics, adjudication, contradiction and lineage.
5. **Memory contract:** event history versus derived memory, tiers/roles, retrieval, consolidation, forgetting, supersession, persistence and reconstruction.
6. **Prediction/outcome contract:** prediction identity and originating sequence, expected outcome, actual observation, delayed/partial feedback, error semantics and attribution.
7. **Goal/decision/action contract:** goal identity/lifecycle, authority, delegation, permission, reversibility, action status, verification and outcome semantics.
8. **Learning contract:** experience lineage, labels/ground truth, train/validation/test separation, update attribution, replay, transfer, interference, adoption and rollback.
9. **Cross-language contract:** schema encoding/versioning, numeric/tensor representation, ownership, timeout/cancellation, error semantics, process failure, compatibility and CPU fallback.
10. **Observability contract:** cycle/activity events, state projections, provenance, privacy filtering, operator authorization, audit and monitoring failure behavior.
11. **Online/offline continuity contract:** Brain/instance identity, local event lineage, authenticated training/synchronization packages, sequence namespace, conflict adjudication, interrupted sync, duplicate/replay and rollback.

These contracts are not all new documents. Their authoritative home should be chosen in the decision register; avoid duplicated definitions.

## 5. Repository evidence limitations and explicit unknowns

The inspected C++ build manifest establishes that the named C++ implementation files are compiled into `jarvis_core`. The inspected test CMake manifest establishes that many named test executables are built and registered with CTest. Neither fact proves all tests passed at the inspected commit, nor that each test has adequate assertions.

The following must not be inferred from this matrix:

- A source file with a mechanism's name does not prove the mechanism is complete, correct or used by the live cognitive cycle.
- A test filename or registered CTest target does not prove meaningful coverage or passing results.
- A C++ static library containing many subsystems does not prove full cross-layer cognition.
- A persisted journal does not by itself prove complete canonical-state reconstruction, rollback detection or production trust.
- A prediction-feedback test does not prove broad general intelligence or robust real-world prediction.
- A Rust `BrainRuntime` and `CognitiveState` exist in the inspected source tree. Its caller/dependency analysis is still required before deciding whether it is active, duplicated, safely bounded or removable.
- TypeScript files define observations, decisions, capabilities, bridge messages and operator sessions; this does not prove a complete monitoring or production transport contract.
- The technology audit did not verify an integrated Python/PyTorch Brain subsystem, CUDA target or Triton kernel path at its inspected baseline. Do not convert this into an unqualified claim that such files do not exist on every branch.
- Online/offline execution and synchronization requirements are documented in the Developmental Brain Plan, but the concrete protocol and instance identity model remain open.
